# 백업과 복구

## 보관 대상

| 자료 | 보관 위치 | 복구에 필요한 것 |
|---|---|---|
| DB 구조 | 이 Git 레포 | 검증한 마이그레이션 버전·커밋, 제품별 설정 |
| PostgreSQL 운영 데이터 | Supabase 관리 백업과 권한 제한된 별도 백업 저장소 | 복구 시각, 암호화된 파일, 체크섬, 복구 담당자 |
| Storage·R2 실제 파일 | 객체 저장소의 별도 백업 또는 버전 관리 | 버킷, 키, 보존 기간, 접근 정책 |
| Auth·서비스 설정 | 비밀 관리 도구와 환경별 설정 기록 | 인증 제공자, 리디렉션, API 노출 스키마, 결제 웹훅, 키 재설정 항목 |

Git에 보관하는 것은 구조와 합성 예제입니다. 실제 고객 덤프, 인증·결제 데이터, API 키와 토큰은 Git에 올리지 않습니다. Supabase DB 백업에는 Storage API 객체의 본문이 포함되지 않으므로 파일은 별도로 보존합니다.

## 앱 데이터 암호화 키 (personal·astro)

personal(`birth_ciphertext`·`input_ciphertext`)과 astro(`*_ciphertext`)는 앱 서버가 AES-256-GCM으로 암호화해 저장합니다. 키가 없으면 DB 백업을 복구해도 해당 열을 읽을 수 없습니다.
- 백업: 키는 비밀 관리 도구(KMS·배포 비밀)에 두고, DB 백업과 다른 위치·권한으로 별도 백업합니다. Git·DB·클라이언트에는 두지 않습니다.
- 버전: 행의 `key_version`으로 어떤 키인지 찾습니다. 키를 바꾼 뒤 옛 키는 재암호화가 끝나고(`key_version < N` 건수 0)도 최소 DB 백업 보존 기간만큼 보존한 뒤 폐기합니다.
- 복구: DB를 복원한 시점의 `key_version` 목록(`select distinct key_version …`)에 해당하는 키가 모두 있는지 먼저 확인하고, 서버에서 표본 행 복호화로 검증합니다.

## 옛 청사진 정리 전 백업

`scripts/cleanup-legacy-blueprints.sh <대상 DB 주소>`는 대상 DB에 적용된 옛 제품 청사진(`supabase/migrations/*_<slug>.sql`) 스키마와 옛 기능 행(`nomad_core.features`·`plan_features`)을 지웁니다. 되돌리는 방법은 백업 복구뿐입니다.
1. 실행 전에 대상 DB 백업을 만들고 백업 시각·체크섬·담당자를 기록합니다(위 "보관 대상").
2. `--dry-run`으로 지울 스키마·표별 행 수·기능 행 수를 먼저 확인합니다(트랜잭션 안에서 실행 후 되돌림). 행이 있는 표가 보이면 그 데이터가 정말 버려도 되는 것인지 확인합니다.
3. 대화형 터미널에서 확인 문구를 직접 입력해 실행합니다(비대화 환경은 거부). 표 목록이 청사진과 다른 스키마(같은 이름의 이식본일 수 있음)는 건드리지 않습니다.

## 복구 연습

1. 복원 대상 제품과 DB 백업 시각, Git 커밋, 객체 백업 시각을 기록합니다.
2. 별도 복구 환경을 준비합니다. 구조만 필요하면 해당 Git 버전의 공통 및 제품 마이그레이션을 새 환경에 적용합니다. 전체 관리 백업을 복원할 때는 복원된 마이그레이션 이력부터 확인합니다.
3. 운영 데이터를 복구할 때는 대상 범위에 맞는 Supabase 복원 절차를 사용합니다. 제품 단독 이전에서는 제품 테이블과 연결된 업체·멤버십·구독·이용권·사용자 ID를 함께 매핑합니다.
4. 객체 파일, Auth 설정과 서비스 환경값을 확인합니다. 테스트 로그인, A/B/C 격리, 구매한 기능, 환불 처리, 파일 다운로드를 검증합니다.
5. 데이터 건수·복구 시각·누락 항목을 기록합니다. 전환이 필요하면 기존 환경의 복귀 경로를 유지하고, 검증을 통과한 뒤 연결을 변경합니다.
