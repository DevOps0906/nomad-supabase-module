# 설계 원칙 8가지

1. **계정은 하나, 데이터는 서비스별** — 로그인·프로필·조직·구독은 `nomad_core`, 서비스 데이터는 각자 `nomad_<slug>` 스키마.
2. **개인도 조직이다** — 개인 가입자도 1인 조직으로 다룬다. 가입 시 자동 생성은 반영 후보([core-schema](../01-architecture/core-schema.md#3-반영-후보)). 팀 전환은 데이터 이전 없이 플랜 변경.
3. **서비스 스키마끼리 연결 금지** — 외래키·조인은 `nomad_core`·`auth`에만. 나중에 서비스를 별도 DB로 분리할 수 있게.
4. **격리가 필요하면 프로젝트를 나눈다** — 병원·학교처럼 민감한 데이터는 별도 Supabase 프로젝트.
5. **RLS가 기본값** — 앱 코드가 아니라 DB가 접근을 막는다. 정책 없는 테이블 금지.
6. **역할(RBAC)은 테넌시와 별개** — 대시보드가 달라지는 것은 역할 문제, 데이터 분리는 조직 문제.
7. **DB가 필요 없으면 만들지 않는다** — DB 없는 서비스는 이 모듈 대상이 아니다. 린 검증 우선.
8. **문서가 먼저, SQL은 초안** — `schema.draft.sql`은 제안이며 확정 시 `supabase/migrations/`로 옮긴다.

## 이 원칙이 나온 배경
- 테넌트 구조와 일반(개인) 구조의 차이: 테넌트는 `organization_id`로 팀 단위 공유, 일반은 `user_id`로 본인 단독.
- 개인/기업 가입을 둘 다 받더라도 90% 이상은 "개인형 + 조직 테이블 확장"으로 시작 가능하다.
- 결제는 조직 단위(제품별 A/B/C 플랜 + 단품), 개인은 1인 조직.
